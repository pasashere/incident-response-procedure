📋 Executive Summary

The goal of this document is to provide an Incident Response (IR) process that is complete enough to be requested during a real incident, yet still usable on shift—especially for an L1 analyst.

The process uses NIST SP 800-61 (r2/r3) as the operational backbone, ISO/IEC 27035-1/2 for governance and “plan / prepare + lessons learned,” SANS PICERL as the easy-to-remember response flow, ENISA for practical triage handling, and FIRST to frame what services a CSIRT typically provides (and what should be escalated). Practical time-pressure insights from Mandiant and CrowdStrike ensure the “first hour” actions stay realistic rather than theoretical.

🌐 Standards Landscape

Globally, the most common “reference set” for IR includes:

  • NIST SP 800-61 — incident handling lifecycle and practical guidance (r2 archived; r3 is current).
  • ISO/IEC 27035-1/2 — incident management concepts, structured process, planning/preparing, and lessons learned.
  • ENISA — practical triage operations (verification → initial classification → assignment) and handling flow.
  • FIRST CSIRT Services Framework — service boundaries (acceptance, analysis, forensic evidence analysis, mitigation/recovery, coordination, crisis support).
  • SANS PICERL — simple operational rhythm responders can remember under stress.
💡
What feels most logical (and easiest to defend to an auditor/management): use NIST SP 800-61r3 as the “spine,” keep ISO/IEC 27035 as the governance wrapper, and teach PICERL as the day-to-day muscle memory. NIST SP 800-53 control IR-4 literally defines incident handling as preparation → detection/analysis → containment → eradication → recovery (and requires an incident response plan).

⚙️ Complete IR Process Steps

This is the full end-to-end process. Even as L1, each phase is documented so the organization can show a complete procedure when asked.

Phase 1 — Preparation

This phase covers setup: roles, escalation paths, communication channels, triage rules, and minimum evidence discipline.

NIST SP 800-61r3 reframes IR as part of broader risk management (not a rare one-off event), and NIST SP 800-53 requires an IR plan plus an incident handling capability aligned to it.

⚠️
Unspecified in this task: tooling (SIEM/EDR/ticketing), retention windows, legal/regulatory reporting triggers, and severity definitions. These are organizational decisions that must be filled in.

Phase 2 — Detection and Reporting

How incidents enter the system: an alert, a user report, a third-party notification, or anomaly detection. The key is that the report is captured consistently and immediately. ENISA’s handling flow starts with incoming reports and then moves to triage.

Phase 3 — Triage + Incident Declaration

Decide: “Is this a ticket? A security event? Or do we declare an incident?”

NIST SP 800-61r2 calls out that organizations should expect false positives and ambiguity during detection/analysis; ENISA breaks triage into verification, initial classification, and assignment.

L1 Deliverable: a clean, timestamped record of what was seen, verified, and escalated.

Phase 4 — Analysis and Scoping

Shift from “one alert” to “what is the blast radius?” Scoping is iterative: confirm → expand scope → confirm again. NIST SP 800-61r2 explicitly shows the lifecycle can loop back to detection/analysis (e.g., when new affected hosts are found).

L1 Deliverable: initial scope hypothesis + evidence pointers (log sources, timestamps, affected identities/assets). If deep forensics is required, that decision is escalated.

Phase 5 — Containment, Eradication & Recovery

Containment stops damage; eradication removes attacker footholds; recovery restores operations safely. NIST SP 800-53 IR-4 explicitly requires these stages.

As L1, broad containment is typically not executed unless pre-approved playbooks exist. Consistent actions: document recommended containment options + impact + urgency and hand them to L2/L3.

Phase 6 — Post-Incident Activity & Improvement

Post-incident review is not optional if process completeness is the goal. NIST SP 800-61r3 emphasizes continuous improvement and integrating lessons learned into ongoing risk management.

L1 Contribution: preserve notes/action log, ensure the timeline is readable, and note what was missing (access, logs, contacts, unclear ownership).

🎯 L1 SOC Playbook — Detection & Triage

Six “always-do” steps for every incident, regardless of type, when the tech stack is unspecified.

Open a Record Immediately

Create a case even if it is “suspected.” Never trust memory during an incident.

Verify the Signal (Quick Sanity Checks)

Check whether the alert/report has enough grounding: correct asset identity, timestamps, event type, obvious false-positive reasons, and whether similar alerts exist.

Classify + Set Initial Severity (Provisional)

Classify type (credential misuse, malware, suspicious admin activity, data exfil suspicion, etc.) and set a provisional severity based on potential impact and exposure.

Scope Lightly (Find the “Neighbors”)

Look for related activity: same user, same host, same IOC, same time window, same destination, repeated pattern. Aim for “minimum useful scoping,” not deep-dive forensics.

Preserve What’s Easy to Lose

Export/attach key logs, screenshots of dashboards, alert payloads, and exact timestamps. If evidence handling is required, stop and escalate before anyone “cleans” the system (per NIST 800-86).

Escalate with a Clear Package

Escalate with: summary, impact guess, scope guess, what was checked, what is recommended next, and what evidence was saved. Never send a vague message.

⏱️ First-Hour Checklists & Timeline

First 20 Minutes

  • Start case + start action log (timestamps in the SOC’s standard timezone).
  • Confirm identity of the affected asset/account (hostname / user / service identity).
  • Pull alert context (raw event, detection rule name, correlation fields).
  • Quick dedupe: is this already known / already being handled?
  • Decide: event under investigation vs incident likely (and escalate if likely).
  • Preserve evidence artifacts without changing systems (exports, screenshots, alert JSON, etc.).

By the One-Hour Mark

  • A one-paragraph incident narrative: “what we think happened so far.”
  • A short list of affected candidates (assets/accounts) + confidence level (“confirmed” vs “suspected”).
  • A “what else could be impacted” note (same user new geos / same IP multiple hosts).
  • Recommended containment options with impact (even if not authorized to execute).
  • Escalation decision (see matrix) and notification sent to the right channel.
  • Clean logs / evidence attached to the case.

Single low-confidence alert, no corroboration, no privileged accounts Yes (for validation / tuning) Not yet Not yet

📌
Unspecified but required for a final version: clear definitions of “critical asset,” severity thresholds, regulated data categories, legal triggers, and who has authority to approve containment actions.
🔑
FIRST alignment: FIRST explicitly separates “incident report acceptance,” “incident analysis,” and “artifact/forensic evidence analysis.” This is why L1 does not attempt full forensic work—evidence is packaged and escalated to the function designed for it.
